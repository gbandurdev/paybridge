## Phase 1: Domain + contracts — Done (2026-11-17)

**Scope:** `src/Domain/` (`Money`, `Currency`, `Capability`, `PaymentStatus`, `Customer`, `NextAction`/`NextActionType`, `PaymentRequest`, `CaptureRequest`, `RefundRequest`, `Payment`, `Refund`, `PaymentEvent`), `src/Status/` (`StateMachine`, `StatusMap`), `src/Exception/` (full hierarchy per PLAN.md §12/§13), `src/Contracts/` (`Gateway`, `Supports*`, `IdempotencyStore`, `LockStore`, `EventStore`, `Transport`/`TransportResponse`). No behavior/IO — pure value objects, enums and interfaces.

**DoD:** `composer test` (97 tests, 211 assertions), `composer stan` (level 9, clean) and `composer cs` all pass. Coverage (`phpunit --coverage-text` with Xdebug) is 100% methods/lines on every class in `Domain/` and `Status/` — verified via clover XML per-class breakdown, not just the aggregate number (the aggregate also folds in `Contracts/TransportResponse`, which is untested by design, see below).

**Decisions made:**
- No new Composer dependencies added. `Contracts/Transport` is deliberately decoupled from PSR-18/PSR-7 (takes method/url/headers/body primitives, returns a plain `TransportResponse` value object) so the PSR-18 adapter can be built in Phase 2 without pulling `psr/http-client`/`psr/http-factory` in before anything consumes them — same "add packages only when used" rule as Phase 0.
- `Capability` enum cases are the union of every capability named anywhere in PLAN.md (§3, §6.2): `AUTHORIZE`, `CAPTURE`, `REFUND`, `REFUND_PARTIAL`, `VOID`, `REDIRECT_FLOW`, `WEBHOOKS`, `THREE_DS`, `PROVIDER_IDEMPOTENCY` — PLAN.md never gives one authoritative list.
- `Contracts/SupportsWebhooks` takes raw `(string $payload, array $headers)` rather than a `WebhookRequest` DTO, since `Webhook/WebhookRequest.php` belongs to Phase 4 (`WebhookHandler`) per the directory layout — avoids forward-depending on a type that doesn't exist yet.
- `Contracts/SupportsRedirect` is an empty marker interface this phase — redirect completion goes through the existing `capture()`/`find()` flows per-driver; PLAN.md doesn't specify extra methods and Phase 6 driver needs aren't known yet.
- `StateMachine::canTransition()` tolerates same-status "transitions" (returns `true`) to support idempotent/duplicate webhook redelivery; actual event dedup is a separate, later concern (`EventStore`, Phase 4).
- `Money`/`Currency` reject floats at the type-hint boundary (`string`-only inputs under `strict_types=1`), reject negative amounts, and reject more fractional digits than the currency's ISO 4217 exponent allows.
- `IdempotencyConflict`'s reason is a backed enum (`IdempotencyConflictReason: IN_PROGRESS | PAYLOAD_MISMATCH`) rather than a bare string, for PHPStan-level type safety.
- Deleted the Phase 0 `tests/Unit/ToolchainSmokeTest.php` placeholder now that real Domain/Status tests exist.

**Next:** Phase 2 — Resilience core (`Pipeline` + middlewares, `RetryPolicy`, `ExponentialJitterBackoff`, `CircuitBreaker`, `RequestFingerprint`, in-memory stores, injectable `Clock`/`Sleeper`).

## Phase 2: Resilience core — Done (2026-11-19)

**Scope:** `Pipeline`/`Middleware` + all six middlewares (`Idempotency`, `CircuitBreaker`, `Retry`, `Timeout`, and pass-through `Logging`/`Metrics`), `RetryPolicy`, `ExponentialJitterBackoff`/`ConstantBackoff`, `CircuitBreaker`, `RequestFingerprint`, the in-memory stores (`IdempotencyStore`, `LockStore`, `EventStore`, plus a PSR-16 `InMemoryCache` backing the breaker), and injectable `Clock` (PSR-20)/`Sleeper`/`RandomSource` with production + fake implementations. Full design/rationale recorded in `docs/plans/phase-2.md` before implementation; see that doc for the per-middleware algorithms and test matrix.

**DoD:** `composer test` (229 tests, 674 assertions), `composer stan` (level 9, clean) and `composer cs` all pass. Coverage: 100% lines/methods on every new/touched class except `InMemoryCache` (PSR-16's `getMultiple`/`setMultiple`/`deleteMultiple`/`clear`/DateInterval-TTL paths are now covered too) — overall 96%+ lines, with the one intentional gap being `IdempotencyMiddleware::resultToArray()`'s defensive `LogicException` branch (unreachable through any real `Gateway` contract, which only ever returns `Payment`/`Refund`).

**Decisions made (beyond PLAN.md §6, full rationale in `docs/plans/phase-2.md`):**
- **`LockStore` interface changed** (Phase 1 contract): `acquire(): ?string` now returns a random owner token instead of `bool`; `release(string $key, string $token)` only deletes on a token match. Closes a real race (holder A's lock expires, B acquires, A's late `release()` must not delete B's lock) — covered by a dedicated test in both `InMemoryLockStoreTest` and `IdempotencyMiddlewareTest`.
- **Idempotency caching is asymmetric by exception type**: a *non-retryable* failure (e.g. `CardDeclined`) stores a `failed` record and replays on retry; a *retryable* failure (network blip, 503, breaker trip) stores nothing, so the next call with the same key tries again from scratch instead of replaying a stale outage for the full 24h TTL.
- **Exact exception class survives idempotency replay**: every `PaymentException` subtype got `toArray()`/`fromArray()`; a new `ExceptionSerializer` validates the stored class via `is_a(..., PaymentException::class, true)` before reconstructing, falling back to a generic `PaymentException` for an unresolvable/tampered class name instead of crashing. `Payment`/`Refund` got matching `toArray()`/`fromArray()` so stored records are plain arrays (JSON-able), never PHP `serialize()` — ready for Phase 4's Redis/PDO stores with no format change.
- **`NetworkException::ambiguous()` flag added**, replacing a blanket "no mutating retries without `PROVIDER_IDEMPOTENCY`" reading of §6.2 with the precise rule: only an *ambiguous* `NetworkException` (a timeout — might have reached the provider) is blocked for mutating ops lacking provider idempotency; `RateLimitedException`, `ProviderUnavailable`, and non-ambiguous `NetworkException` (e.g. connection refused before anything was sent) retry normally regardless. `TimeoutMiddleware` sets `ambiguous: true` when it wraps an unclassified timeout-shaped failure.
- **`CircuitOpen` now implements `RetryableException`**, so `IdempotencyMiddleware` treats a breaker trip like any other transient failure (stores nothing) instead of permanently caching it as a terminal failure for that idempotency key. Verified safe for `CircuitBreakerMiddleware` itself both structurally (its `throw CircuitOpen` sits outside the `try` that wraps `$next`, so it can never be fed back into its own failure-counting branch) and by a dedicated test asserting a burst of calls made entirely while open never changes `consecutiveFailures`/`openedAt`.
- **`CircuitBreaker` state is backed by PSR-16** (`Psr\SimpleCache\CacheInterface`, new `psr/simple-cache` dependency) rather than a bespoke store, matching §6.4's "shared across workers" requirement and §2's existing PSR-16 mention; `CircuitBreaker` (pure state machine) and `CircuitBreakerMiddleware` (exception-classification + wiring) are split per the directory layout.
- **New `psr/clock` dependency** for `Contracts\Clock extends Psr\Clock\ClockInterface`. `SystemClock` lives in `src/Clock/`; only test doubles (`FakeClock`, `FakeSleeper`, `FakeRandomSource`) live in `src/Testing/` — real implementations (`RealSleeper`, `SystemRandomSource`) sit beside their own interfaces in `src/Resilience/`.
- **`Logging`/`MetricsMiddleware` are intentionally pass-through** this phase — real PSR-3/PSR-14 wiring needs `Http/Redactor` (not built yet) and an actual logger/dispatcher from `PaymentManager::fromConfig()` (Phase 4); they exist now only so the `Pipeline`'s full six-middleware order is structurally in place.
- `PaymentException::fromArray()` deliberately never uses `new static()` (PHPStan-unsafe in a non-final base class) — it always builds a plain `PaymentException`. Every subtype that needs its own identity preserved on replay (including the "no extra fields" ones — `CardDeclined`, `AuthenticationFailed`, `UnsupportedOperation`, `InvalidSignature`, `InvalidRequest`, `CircuitOpen`) defines its own `fromArray()` using `new self()`, which is safe because each of those classes is `final`.

**Next:** Phase 3 — `FakeGateway` + `GatewayContractTestCase` (charge/find/refund/void/webhook verify-parse/error mapping/capability enforcement), proving the Phase 2 pipeline end-to-end through a real (fake) driver.

## Phase 3: FakeGateway + contract test suite — Done (2026-11-19)

**Scope:** `src/Drivers/Fake/FakeGateway.php` (scriptable, capability-gated test driver implementing `Gateway` + every `Supports*` interface), `src/Middleware/PipelineGateway.php` (production wrapper that runs any driver through the full resilience pipeline — reused as-is by `PaymentManager` in Phase 4), `tests/Contract/GatewayContractTestCase.php` (the reusable driver conformance suite every future driver extends), `tests/Contract/WebhookFixture.php`, `tests/Contract/PipelineTestMiddlewares.php` (shared test-pipeline wiring trait), `tests/Contract/FakeGatewayContractTest.php`, `tests/Unit/Drivers/Fake/FakeGatewayTest.php`, `tests/Unit/Middleware/PipelineGatewayTest.php`. Full design/rationale in `docs/plans/phase-3.md`.

**DoD:** `composer test` (252 tests, 736 assertions, including a new `contract` PHPUnit testsuite), `composer stan` (level 9, clean) and `composer cs` all pass. `FakeGatewayContractTest` wraps `FakeGateway` in `PipelineGateway` for every assertion, so the suite passing *is* the literal DoD: "FakeGateway passes the contract suite through the full middleware pipeline."

**Decisions made (full rationale in `docs/plans/phase-3.md`):**
- **Capability gating, not interface gating, inside `FakeGateway`.** It implements every `Supports*` interface unconditionally; a constructor-supplied `list<Capability>` decides what actually works, and every method checks it first, throwing `UnsupportedOperation` before touching any state. Mirrors how a real driver must behave (PLAN.md §3.2) and is what makes capability-enforcement testing possible at all.
- **`PipelineGateway` always structurally implements every `Supports*` interface too** (per instruction, so `PaymentManager` can wrap any driver and get one consistent type back). Direct consequence: `$pipelineGateway instanceof SupportsRefund` (etc.) is *always* `true` once wrapped, regardless of what the inner driver supports. This is why **`GatewayContractTestCase` gates every scenario on `$gateway->capabilities()` membership, never on `instanceof Supports*`** — capabilities() is the one signal the wrapper can't paper over (it delegates straight through to the inner driver). `instanceof` checks still appear in the suite, but purely to narrow PHPStan's type after capabilities() already decided the test applies, and they fail loudly (not skip) if they somehow don't hold.
- **Hook nullability is now capability-driven, not blanket-optional** (revised after initial user feedback): `createGateway()` and `successfulChargeRequest()` are required, non-nullable — they alone back charge/find/full-refund/partial-refund, no separate "refund scenario" hook needed. `redirectTriggeringRequest()`/`voidableAuthorizeRequest()`/`validWebhookFixture()`/`tamperedWebhookFixture()` may return `null` **only** when the gateway doesn't declare the matching `Capability`; if it does declare it, a `null` hook **fails** the test by name via a shared `assertCapabilityHookConsistency()` helper (checked in both directions — a non-null hook paired with an undeclared capability also fails). `decliningRequest()` and `createGatewayWithoutCapability()` stay purely optional (no `Capability` enum value names "can decline," and varying the capability set is a different question from currently declaring one).
- **`REFUND_PARTIAL` has no dedicated hook.** Unlike `VOID`/`WEBHOOKS`/`REDIRECT_FLOW` (which gate whether an entire operation is reachable, so testing their absence needs a capability-removed gateway variant), `REFUND_PARTIAL` gates a sub-behavior of `refund()` that's already reachable through the required `successfulChargeRequest()`. `testPartialRefundRespectsCapability()` branches on the *same* gateway's `capabilities()` directly — no `createGatewayWithoutCapability()` variant needed, and no separate enforcement test (it would just duplicate the negative branch already in that one test).
- **`FakeGateway::willFail(string $operation, string $exceptionClass, int $times)`** is scoped per operation (`charge|find|refund|capture|void`; `authorize` is intentionally not scriptable, matching the user's explicit list), queued and consumed at the top of each method (after its capability check, before its real logic) — so scripting one operation never leaks into another's internal lookups (a private `lookup()`, not the public `find()`, backs `capture`/`refund`/`void`'s own reference lookups for exactly this reason). `thenSucceed(): void` is a readable no-op terminator, not `self`-returning, since PHPStan correctly flags a chainable-but-side-effect-free method's unused return as dead code.
- **No separate `FakeStatusMap`.** `FakeGateway` never receives a foreign provider vocabulary to translate — its webhook payloads already speak `PaymentStatus`'s own string values — so there's nothing for a `StatusMap` to do here; real drivers (Stripe/PayPal) are the ones that need one.
- **`FakeGateway::find()` on an unknown reference, and any illegal `StateMachine` transition, throw `InvalidRequest`** — reusing the existing exception rather than adding a dedicated "not found" type for a case PLAN.md never names.
- **`Pipeline`'s constructor binds one terminal callable per instance**, so `PipelineGateway` can't hold a single reusable `Pipeline` across operations with different terminals — it stores the `list<Middleware>` instead and builds a fresh `Pipeline` per call. No change to `Pipeline` itself.
- `phpunit.xml.dist` gained a `contract` testsuite (`tests/Contract`) alongside `unit`; PHPUnit skips the abstract `GatewayContractTestCase` base automatically, so only `FakeGatewayContractTest` actually runs today.

**Next:** Phase 4 — `PaymentManager::fromConfig()`, gateway registry, `withFallback()`, `WebhookHandler` with dedup, persistent stores (PSR-16/PDO/Redis), and a `Reconciler`. `PaymentManager` should wrap every registered driver in the now-existing `PipelineGateway` rather than re-deriving pipeline wiring.

## Phase 4: Manager, webhooks, persistent stores — Done (2026-11-19)

**Scope:** `PaymentManager` (+ `Config\GatewayConfig`/`Config\ResilienceConfig`, gateway registry via `extend()`, lazy+memoized `gateway()` resolution), `FallbackGateway` (`withFallback()`), `Webhook\WebhookHandler`/`WebhookRequest` + `Contracts\PaymentStatusLookup`, `Reconciliation\Reconciler`/`ReconciliationCandidate`, the PSR-16 cache / PDO / Redis store implementations (`Store\Cache\*`, `Store\Pdo\*` + SQL migrations + `Pruner`, `Store\Redis\*`), `Store\StoreFactory`, three new PSR-14 events (`Event\WebhookReceived`, `Event\WebhookIgnoredStale`, `Event\PaymentStatusChanged`), and `examples/plain-php`. Full design/rationale in `docs/plans/phase-4.md`.

**DoD:** `composer test` (367 tests, 946 assertions — 6 skipped: the Postgres/MySQL integration tests, which have no reachable server in this environment), `composer stan` (level 9, clean) and `composer cs` all pass. `examples/plain-php/run.php` runs successfully end-to-end against **both** the PDO/SQLite and the Redis backend (verified by actually running it against a real `redis-server` once `ext-redis` was installed — see the 2026-11-19 update below), each confirmed repeatable across consecutive runs. Overall `src/` line coverage is 92.70%.

**Decisions made (full rationale in `docs/plans/phase-4.md`; user corrected three points on the first draft, folded in below):**
- **`Contracts\EventStore` gained `claim()`/`release()`** (additive, user-approved) to close a real duplicate-webhook-processing gap plain `has()`/`remember()` couldn't close: `claim()` is atomic where the backend allows it (`PdoEventStore`/`RedisEventStore`; `CacheEventStore` stays non-atomic, documented, same PSR-16 ceiling as `CacheLockStore`). `WebhookHandler` claims with a **short** processing TTL (`claimTtlSeconds`, default 300s) and only extends it to the long-term 7-day dedup window via `remember()` *after* processing succeeds — a worker that crashes mid-processing (never reaching `remember()`/`release()`) self-heals after 5 minutes instead of blocking every redelivery for a week. A processing failure explicitly `release()`s the claim and rethrows, so the webhook controller returns 5xx and the provider's own redelivery is claimed fresh, not treated as a false duplicate.
- **Webhook stale-transition detection is opt-in via `Contracts\PaymentStatusLookup`** (`findStatus(gateway, providerReference): ?PaymentStatus`), not built into `WebhookHandler`/`Reconciler` unconditionally — PayBridge has no payment ledger of its own anywhere in its directory layout, so there's no "current status" to diff against unless the app supplies one. Both `WebhookHandler` and `Reconciler` share this one contract: a legal `Status\StateMachine` transition dispatches `Event\PaymentStatusChanged`; an illegal one dispatches `Event\WebhookIgnoredStale` (webhook only — the event is still claimed/remembered so the provider gets a 200) or is silently skipped (`Reconciler`, which has no "ack" concept). A `null` lookup result (lookup absent, or the app genuinely doesn't know the reference yet) skips the diff entirely rather than guessing.
- **`FallbackGateway`'s fallthrough rule is deliberately narrower than "any `RetryableException`"** (user correction on the first draft): only `CircuitOpen` (the breaker never let the call reach the provider) and a **non-ambiguous** `NetworkException` (`!$e->ambiguous()`, e.g. connection refused before a byte was sent) fall through to the next configured gateway. `RateLimitedException`, `ProviderUnavailable`, an **ambiguous** `NetworkException` (a timeout — the provider may have already processed the request), and every non-retryable failure all rethrow immediately — falling through any of those risks charging the same order twice through two different processors. Only implements `Gateway`'s core (`name/capabilities/charge/find`), not every `Supports*` interface; `capabilities()` delegates to the first configured name (documented simplification, not a true intersection).
- **PDO stores gained `purgeExpired(): int` + a `Store\Pdo\Pruner`** (user addition): `DELETE WHERE expires_at <= ?` on each of the three tables, bound from the injected `Clock`. Not added to the PSR-16/Redis stores — their own TTL mechanisms already expire keys without a manual sweep; only PDO rows are "dead but still present." `Pruner` owns no scheduler itself, meant to run from cron, same spirit as `Reconciler`.
- **`Config\GatewayConfig` validates gateway names** against `/^[a-z0-9_-]+$/` (user addition) — the name ends up in a future webhook route segment (`/_paybridge/webhook/{gateway}`, §11.3) and in log/metric labels, so a bad name fails at `fromConfig()` time instead of silently producing an unaddressable gateway.
- **`docs/PLAN.md` §12 Phase 5 gained an explicit requirement** (user addition): the Laravel bridge's default `LockStore` must be `Cache::lock()`-backed and the Symfony bridge's must be `symfony/lock`-backed — never this package's own `Store\Cache\CacheLockStore` by default, since that class is explicitly documented as a non-atomic, dev/single-process-only fallback (PSR-16 has no compare-and-set primitive) and both frameworks already ship a real distributed lock.
- **`PaymentManager::fromConfig()` resolves gateways lazily and memoizes them**, rather than building every configured `Gateway` eagerly: `extend()` is only useful as an instance method called *after* `fromConfig()` returns (per PLAN.md's own example), so eager construction would make a driver registered via `extend()` too late for anything resolved during construction.
- **The circuit breaker's PSR-16 cache defaults to the `idempotency` store's own driver/DSN** when `stores.cache` is absent, rather than silently defaulting to in-memory — the in-memory default would quietly break §6.4's "shared across workers" the moment someone configures Redis/PDO for idempotency but leaves `cache` unset (exactly what §5's own example config does). This only works when the idempotency driver is itself `inmemory`/`cache`; `Store\StoreFactory::cache()` deliberately rejects `pdo`/`redis` (no bespoke PSR-16 adapter was built over either, since nothing else in this phase needs one) — a deployment using `pdo`/`redis` for idempotency **must** configure `stores.cache` explicitly (`examples/plain-php/run.php` does this and documents why inline).
- **`IdempotencyMiddleware`'s private `"idem:{gateway}:{key}"` composite-key string is parsed back apart by `PdoIdempotencyStore`** (strip the `idem:` prefix, split on the first remaining `:`) to populate the DoD-mandated two-column `(gateway, idempotency_key)` unique constraint — a real, acknowledged coupling, accepted rather than changing the Phase 1 `IdempotencyStore` interface to take `$gateway`/`$key` separately.
- **PDO migrations are one directory per engine** (`Store/Pdo/migrations/{sqlite,pgsql,mysql}/0001_create_tables.sql`) since PK/auto-increment syntax differs; `Migrator::migrate()` detects the driver via `PDO::ATTR_DRIVER_NAME` and is idempotent (checks whether `paybridge_idempotency` already exists before applying anything, via a try/catch `SELECT`, not a tracked migrations table — a full tracking system is Phase 5 bridge territory).
- **Redis stores use ext-redis's built-in `\Redis` class directly, not `predis/predis`** — keeps this phase's "zero new Composer dependency until something actually needs it" rule intact; PHPStan's own bundled `Redis` stub type-checks `src/Store/Redis/*` even though this development environment has no ext-redis installed.
- Three new PSR-14 events only (`WebhookReceived`, `WebhookIgnoredStale`, `PaymentStatusChanged`) — the other five named in §10 still depend on real `Logging`/`MetricsMiddleware` wiring, which needs `Http/Redactor` (not built, not in this phase's own directory-layout bullet).

**Known, accepted coverage gaps** (same "defensive branch, unreachable through any real contract" category Phase 2 already established for `IdempotencyMiddleware::resultToArray()`): `Migrator`'s `default => throw` branch for a PDO driver name outside `sqlite|pgsql|mysql` (no real PDO connection ever reports one); each PDO store's `catch (\PDOException $e) { if (!$this->isConstraintViolation($e)) throw $e; }` rethrow branch (would need real fault injection, e.g. a disk-full error, to trigger honestly).
